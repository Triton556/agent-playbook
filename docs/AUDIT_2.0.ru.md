## Ясность и статическая проверка триггеров

Это анализ инструкций, **не измеренная частота вызовов моделью**:

- «Почини наблюдаемый crash» → dev-debug; описание исключает новый feature-plan.
- «Сделай согласованную кнопку» → dev-implement / ui-design; не новое creative interview.
- «Оцени читаемость уже открытого экрана» → ui-review, actual result, не исходный hash.
- «Ты мозг, продолжай этот проект» → сохранённый профиль/worker identities, не повтор setup interview.
- «Выполни эту Story на Jam Board» → Jam; просто подключённый MCP не триггер.
- «Ответь на общий вопрос» → нет основания открывать orchestration/KB capture без нового полезного знания и активной интеграции.

Примеры замены: vague «хорошо проверить» → изменённый сценарий, ожидаемый результат, отрицательный случай и evidence; «все проверки ещё раз» → релевантные риски и stop после достаточного успеха; «найди лучшую идею» → согласованный критерий выбора и конкретное ограничение. Эти локальные правила применяют рекомендации OpenAI, но не выдаются за дословные требования поставщика.

## Проверка

Финальный Linux/Python3.12 прогон с контрактом Jam: **75 тестов,75 прошли,0 пропущены**. Проверены реальные install/verify/remove разных клиентов, upgrades старых релизов (включая1.6), неизменённые owned obsolete files, отказ на edited files до записи, сохранение unowned соседей/чужих навыков, явные closures, helpers и instruction ownership. Первый прогон использовал portable contract и пропустил две проверки внешнего приложения. Затем подключён read-only checkout Jam Board `cf2e8fd03d5753a9ea316c9408e6da9f74f0cbc7` через `JAM_BOARD_DOC_PATH`: найдены и исправлены устаревшие connection snippets (project pinning) и fixture39→45tools; все6 Jam-проверок прошли, включая wait_for_changes. Это сверка контракта/примеров, не live MCP end-to-end.

Проверки manifest/diff дополняют функциональные тесты, не заменяют их. Windows выполняется отдельно в GitHub CI. Нет оплаченного model A/B, измерения токенизатором или проверки реального рабочего Mac. Контрольный model pilot при необходимости: одна версия модели/effort, одинаковый snapshot/task/tools/budget, отдельные чистые профили, заранее заданные acceptance, по нескольку повторов; сравнивать качество, вызовы, задержку, input/output/cache отдельно. Без этого причинный вывод «модель стала умнее» не установлен.
