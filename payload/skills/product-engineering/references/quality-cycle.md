# Quality cycle for authored artifacts

Use for a creative or visual deliverable with several outputs, procedural generation, repeated feedback, or a semantic defect. A small text edit or an unchanged screen needs only its affected checks. Continue ordinary repairs under the existing scope; this procedure adds evidence, not another approval stage.

## 1. Reconcile the brief before committing work

Read the supplied critique and the saved artifact/report it names before deciding an implementation plan or delegating implementation. An agent can independently inspect a source, but its implementation brief must state reviewed facts, hypotheses, accepted intent and unresolved conflicts. A summary is a retrieval aid; important thresholds and contradictions need the original source.

Record four short contracts in the project's existing plan or quality ledger:

- **Objective:** what a viewer should recognize, understand or do; the expected consequence.
- **Style:** intended simplification and character, positive exemplars to retain, rejected tendencies. Greater detail and realism are separate choices.
- **Function:** working face, affordance, support, contact or dependency that makes the object/scenario coherent.
- **Context:** actual scale, camera/distance, platform, era/biome, material/use, asset vs scene, editable vs rendered output.

Turn feedback into requirements with blocking/advisory scope, affected subjects, and a check that can distinguish success from the reported failure. Record protected files or approved exemplars as immutable baselines; fixes and optional variants get new versions. A keep verdict from a secondary audit does not erase a later specific human correction.

Completion: each planned change has a criterion and an evidence method; conflicting claims have a stated resolution or a targeted next observation.

## 2. Resolve critical uncertainty

Use [reference grounding](reference-grounding.md) for observable triggers, sufficient bases and exceptions. An unexplained critical function/proportion/interaction, contradictory source, identity-breaking reuse, unassessable required feature or repeated unexplained defect blocks only its dependent expensive step. Continue permitted independent work. A feature's basis is an inspected source or a permissible authored choice, with a planned check and remaining unknown.

Completion: the relevant uncertainty is resolved by usable evidence or explicitly retained; unrelated beauty and link counts cannot substitute.

## 3. Build structure before decoration

For a new concept, expensive implementation or batch, test one inexpensive representation and relevant extremes before scaling. An unchanged accepted basis can be reused. Use a deterministic baseline and one representative result before a batch. Name functional components, contacts, negative spaces, moving clearances, scene layers and expected context. Choose variation by cause: gravity, deposition, erosion, use, growth or deliberate stylization. Match materials, shape and scale to that story. Noise or extra colors alone do not establish age or realism.

For a batch, test representative extremes (largest mass, finest detail, crowded contacts, compositional exception). Shared helpers need class parameters and an identity check; reuse of a wheel module should preserve vehicle class, just as reuse of a UI component should preserve its meaning. Save generator dependencies, seed/parameters, output revision and camera/scale contract.

Completion: the structure, use and intended style read in the intended view before the expensive detail pass.

## 4. Inspect three separate layers

Use the [shared human-perspective review](human-perspective-review.md) for audience conditions, first reading, style/context/comprehension/use, observation versus cause and preservation. These criteria use the existing ledger kinds and evidence; they do not require a new global schema or extra agent. The UI branch specifies interaction checks; other media use their actual modality.

| Layer | Evidence | Failure that this detects |
| --- | --- | --- |
| Technical | Bounds/format/roundtrip, consistency, build, measured budgets, deterministic reproduction | Broken file, stale output, invalid format or behavior |
| Semantic | Functional feature, allowed contact vs forbidden collision, causal/context invariants, scale relationships | Valid files with an unusable grip, hidden door, impossible mooring, misleading chart |
| Visual | Actually inspected images and interactions at intended human scale, useful views/crops, neutral and intended rendering | Technically valid detail that is illegible, wrong emphasis, lost style, misleading framing |

Use the actual target rectangle. Add mobile/narrow review when it is a product requirement or a affected layout, not because every artifact is a website. A model review names the functional front and distinct views; repeated before/after frames at the same angle are not additional directions. Category comparison uses common world scale when judging proportions; per-object fit is separately labeled for shape/detail.

Ask the disconfirming questions: what is it, what is its action, what holds it, what is hidden, what intersects or floats, what belongs here, what makes it feel lived in, what did this change make worse? Zoom into faces, hands or key controls if the overview cannot decide. Human acceptance is only recorded from actual human feedback; self-review is named self-review.

Completion: every blocking criterion has current relevant evidence; unresolved or unavailable checks remain pending, failed, or nonapplicable with a reason. A build pass does not fill the semantic/visual columns.

## 5. Repair, recheck, retain lessons

Declare required outputs before a batch and bind each to its relevant checks; absent or partial output cannot disappear from acceptance. Record a defect as trigger → observation → affected revision → hypothesis → repair → recheck. Group by cause so one fix prevents a class of mistakes. Re-run the affected checks after changes, plus a bounded regression of protected exemplars and shared helpers. When a check fails, retain the failing receipt; update the next hypothesis rather than repeating the same action or requesting permission already granted.

For multi-output/repeated-defect work, use `quality_ledger.py` against the local project. Its `snapshot` command hashes the declared source/artifact closure; `validate --require-ready` checks current evidence, required views, blocking issues and protected files. Replace receipts after relevant changes, not only status labels. It cannot authenticate a reviewer, detect undeclared dependencies, or judge the actual aesthetics.

Keep **automated readiness**, **agent visual review**, and **human acceptance** separate. Defer optional polish with a reason; a still-blocking defect cannot become complete by renaming it deferred. External tool/access failure stays a concrete blocker for the dependent check while independent work continues.

Promote a lesson to reusable instructions only with its trigger, mechanism, check, evidence, scope/exceptions and a representative successful/counterexample pair. Put general completion/evidence behavior here, representation-specific rules in the relevant skill, and project-specific values in the project. Version examples and refer to saved artifacts rather than loading entire studies into every chat. Separate confirmed perceptual observations from verified technical mechanisms; active example pairs are a compact selection, not a limit on the retained corpus.

Completion: the repaired scenario is checked at its current revision, protected examples are preserved, and the next agent can identify the current status and next authorized step from the saved state.
