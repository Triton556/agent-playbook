# Обратная разработка и REA

Эта ветка выбирается для исследования устройства приложения/бинарника/протокола, реконструкции поведения и анализа Electron/ASAR/.NET/native артефактов. Само наличие источника или метода не подтверждает доступ, установку либо разрешение активной цели.

1. Через kb-find прочитай общую рамку безопасности и относящуюся проектную заметку. Для методологии используй `{{MEMORY_ROOT}}/PROJECTS/Маршрутизатор безопасности и обратной разработки.md`. Исторические 43 маршрута и старые проверки не являются проверкой текущего ПК.
2. Установи цель, артефакт, разрешённую среду и нужный уровень: исходники/поведение/байткод/native. Начинай с доступной статической инвентаризации; активное взаимодействие — в собственной либо явно разрешённой тестовой среде по действующей рамке.
3. Проверь реальные доступные инструменты/MCP и их capabilities. [REA](https://github.com/morluto/rea) — кандидат для связанного анализа приложений, JavaScript/Electron, .NET, websites и native binaries. По README статический JS не требует native engine; для native используются Hopper/Ghidra/IDA. Список поддержек уточняй по текущей документации при работе.
4. REA MCP в рамках данного UI/workflow пакета не регистрируется. Перед использованием проверь, установлен и подключён ли он; отсутствующий toolkit не изображай доступным. Системная установка/регистрация нового доступа — отдельный конкретный шаг, без автоматического setup из ссылки.
5. Веди Evidence → Finding → Path по проектной методологии. Привязывай вывод к артефакту, пути, команде и наблюдению; отделяй статическую гипотезу от воспроизведённого поведения. Для разрешённой реализации результата на своём проекте переходи в [product-implementation](../../product-implementation/SKILL.md).
