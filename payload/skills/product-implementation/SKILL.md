# Реализация

Вход — ясная задача либо согласованный план; результат — работающий сценарий и подтверждающие проверки. Прочитай относящиеся файлы и незакоммиченные изменения, найди принятые компоненты, контракты и команды проекта. Если цель ясна, выполняй обычные технические шаги самостоятельно.

Работай вертикальными срезами: действие пользователя → необходимые слои → наблюдаемый результат → проверка. Заверши полезный срез прежде, чем расширять поверхность. При длинной реализации по спецификации используй [implement](vendor/matt-pocock/implement/INSTRUCTIONS.md) как источник метода; делегирование и git-публикации определяются действующими разрешениями.

Сначала используй существующие модули и контракты. Когда изменение упирается в неудобную границу модуля, адресно прочитай [codebase-design](vendor/matt-pocock/codebase-design/INSTRUCTIONS.md), затем нужную справку. Выбирай реальную точку проверки и компактный интерфейс; архитектурное расширение за пределы задачи обсуждается по общим правилам.

- Для UI до выбора композиции и компонентов загрузи [product-ui-design](../product-ui-design/SKILL.md). Демо, заглушки и искусственные данные отмечай; заявленный рабочий сценарий подключай к реальному поведению.
- Для нетривиального сбоя загрузи [product-debugging](../product-debugging/SKILL.md) с симптомом и фактическим выводом.
- Для затронутого поведения и итогового ревью загрузи [product-testing](../product-testing/SKILL.md); объём проверки определяется риском изменения.
- После изменения UI подключи [product-ui-review](../product-ui-review/SKILL.md) для проверки реального render и действий.

Исправляй существенные дефекты, обнаруженные в согласованном объёме, затем повторяй затронутые проверки. Сдавай после последних изменений: что работает, где результат, как запустить, какие проверки проведены и что ограничено. Если пользователь запросил лишь отдельный этап, закончи на нём. Навыки не разрешают самостоятельно расширять доступ, расходы или публикацию.

Исходная ревизия и лицензия: [sources.json](sources.json), [LICENSE](licenses/mattpocock--skills-LICENSE).

Для серии создаваемых артефактов или повторного смыслового дефекта используй [цикл качества](../product-engineering/references/quality-cycle.md): критерий и способы проверки перед массовой генерацией; исправление → актуальное свидетельство → затронутая регрессия. Обычный небольшой срез сохраняет соразмерный процесс.

При нескольких выходах или длинной реализации используй [состояние этапов и полноту](../product-engineering/references/task-state.md). Держи список обязательных результатов стабильным; этап передаёт артефакт/ревизию, актуальные свидетельства, открытое и следующий критерий. Пропавший, частичный и заблокированный выход не становится готовым. При критическом неизвестном применяется [reference-grounding](../product-engineering/references/reference-grounding.md). Для UI согласуй состояние данных, сохранение работы и восстановление по [interaction-quality](../product-ui-design/references/interaction-quality.md); заверши реальным поведением, а не обещанием или декоративным откликом.
