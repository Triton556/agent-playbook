# Планирование разработки

Результат — достаточный для исполнения план в масштабе задачи. Начни с запроса, существующего поведения и уже принятых решений. Материалы Matt Pocock в [to-spec](vendor/matt-pocock/to-spec/INSTRUCTIONS.md) полезны для неполного брифа; обязательное интервью и внешние публикации из оригинала заменены текущими правилами работы.

1. Установи пользователя, его действие и наблюдаемый результат. Отдели согласованные требования от предположений; проверь существенные предположения по репозиторию, документам или доступному исследованию.
2. Найди существующие точки интеграции, данные, контракты и ограничения. Сравни варианты только для решений с заметным влиянием на продукт, сложность, стоимость или обратимость. Обычные технические детали принимай самостоятельно.
3. Уточни одним коротким набором вопросы, без которых меняются цель или архитектура. Уже отвеченное считай контекстом. Пока ждёшь, заверши независимый анализ. Неясность малой детали не должна останавливать весь план.
4. Разложи реализацию на проверяемые пользовательские сценарии, укажи зависимости и критерии приёмки. Для рискованной миграции или выпуска добавь подходящий способ проверки и восстановления. Используй существующий формат проекта; для небольшой задачи достаточно плана в сообщении.

Для существенного UX-решения подключи [product-ui-design](../product-ui-design/SKILL.md) в режиме проектирования. Предметные термины и ADR требуют domain-modeling только когда это действительно результат задачи.

Готовый план связывает требования с реализацией и проверкой: что меняется, где, какие решения приняты, как подтвердить результат и что ещё неизвестно. При запросе только на план отдай его. В уже разрешённой полной разработке переходи в [product-implementation](../product-implementation/SKILL.md) без повторного «продолжать?». Существенные решения согласуются по действующим правилам.

Исходная ревизия и лицензия: [sources.json](sources.json), [LICENSE](licenses/mattpocock--skills-LICENSE).

Для нового/неоднозначного результата задай условия пользователя (предзнание, режим внимания, устройство/масштаб/темп, цена ошибки), конкретные признаки стиля/контекста и список обязательных выходов. Используй известные решения без нового интервью. При критическом неизвестном прочитай [основания и референсы](../product-engineering/references/reference-grounding.md); уверенность модели не закрывает триггер. Для дорогой реализации/серии выбери дешёвое представление и рискованные крайние случаи; не повторяй этот этап для принятой неизменённой основы.
