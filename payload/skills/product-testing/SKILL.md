# Тестирование и ревью кода

Выбери режим по результату запроса: проверка готового изменения, добавление тестов, TDD или review-only. Определи проверяемую ревизию/рабочий diff, требования и риск. Результат проверки должен относиться к фактическому состоянию, включая релевантные незакоммиченные изменения.

## Проверка поведения

Проверь команды и инфраструктуру проекта. Выполни применимые type/build/lint и сценарии, которые различают правильное и ошибочное поведение. Каждому существенному критерию приёмки должно соответствовать свидетельство либо явный пробел. Выбирай минимальный достаточный набор; общий suite нужен по требованиям проекта или широте риска.

Новые поведенческие тесты наблюдают результат через публичную границу. Ожидаемое значение берётся из контракта, спецификации или проверенного примера, а не из повторения вычисления реализации. Используй реальные существующие test seams; внешние недетерминированные границы изолируй там, где это сохраняет смысл проверки.

Для финансовой логики тесты обязательны. Для существенной логики и регрессий добавь failing test до исправления, когда это применимо. Простая обратимая визуальная правка может проверяться render/сценарием и существующими проверками. Если нужен TDD или сложный выбор test seam, прочитай [tdd](vendor/matt-pocock/tdd/INSTRUCTIONS.md) и адресно [tests](vendor/matt-pocock/tdd/tests.md) либо [mocking](vendor/matt-pocock/tdd/mocking.md). Предварительное согласование каждого test seam из оригинала заменено действующими правилами существенных решений.

В TDD двигайся одним наблюдаемым поведением: red → минимальная реализация → green → уместный рефакторинг → повтор затронутой проверки. Flaky тест требует оценки условий и повторяемости; один зелёный прогон не доказывает устранение нестабильности.

Проверь покрытие смысловых критериев отдельно от технических: наличие детали в коде или валидном файле не доказывает её функцию, контакт, масштаб либо читаемость. Для повторного дефекта добавь проверку, которая воспроизводит конкретный провал. Свидетельство относится к проверенной ревизии и значимым зависимостям; после их изменения повтори затронутую проверку. Для серии результатов используй [цикл качества](../product-engineering/references/quality-cycle.md) и его локальный ledger, не заменяя непройденные критерии количеством зелёных тестов.

## Ревью

Для review-only или существенного diff проверь соответствие требованиям и паттернам проекта; при необходимости прочитай [code-review](vendor/matt-pocock/code-review/INSTRUCTIONS.md). Работай текущим агентом по действующим разрешениям. Это самопроверка, если ты же писал изменение.

Находка должна описывать реальный триггер, неверное поведение, влияние и место в коде. Приоритет отдавай пропущенным требованиям, регрессиям, ошибкам данных и контрактов. Вкусовую рекомендацию отделяй от дефекта. Для review-only отдай находки и пробелы проверки; при разрешённой реализации исправь существенные дефекты и перепроверь.

## Завершение

Падение проверки передай в [product-debugging](../product-debugging/SKILL.md) вместе с точным выводом. Для UI используй [product-ui-review](../product-ui-review/SKILL.md): сборка и unit-тесты не подтверждают визуальное качество.

Отчёт содержит выполненные команды/сценарии, результат, найденные дефекты и непроведённые проверки. После последних изменений повтори затронутые проверки; повтор общего suite без нового основания не нужен. Готовность подтверждают критерии задачи и свидетельства, а не только отсутствие находок на ревью.

Исходная ревизия и лицензия: [sources.json](sources.json), [LICENSE](licenses/mattpocock--skills-LICENSE).

Для многоэтапного/серийного результата сверь обязательные выходы и [текущее состояние](../product-engineering/references/task-state.md), а не только число зелёных проверок. Изменение зависимости инвалидирует затронутое свидетельство; при неизвестной независимости действует консервативная перепроверка. При UI-состояниях используй применимую ветку [interaction-quality](../product-ui-design/references/interaction-quality.md): главный результат, отказ/восстановление, сохранность ввода, фильтры и запоздалые ответы. Наблюдение аудита проверяется до исправления по предполагаемой причине. Для запрошенной проверки workflow используй [пилот и метрики](../product-engineering/references/workflow-pilot.md); описанный кейс не считается выполненным.
