# Проектная основа UI: сценарий, стиль и связанные состояния

Для нового сценария, существенного редизайна или серии экранов проверь проектную основу до полной реализации. Перенос из voxel — паспорт, согласованные представления, проверка замысла и сравнение с результатом. В UI представления связаны действиями, данными и адаптацией к окну; их число определяется сценарием.

Используй существующий план/дизайн-документ проекта и ссылки на макеты. Отдельный паспортный файл, JSON-схема, Figma или генерация изображений не обязательны. Для ясной локальной правки достаточно записи о затронутом свойстве, состояниях и проверке. Принятая неизменённая основа переиспользуется; новый сценарий, изменённый смысл действия, визуальная система или неподтверждённый размер окна требуют адресного дополнения.

## 1. Записать паспорт сценария

Если существенные требования размыты, сам проведи [опрос по темам и сохранение задания/приёмки](../../product-engineering/references/task-brief-and-acceptance.md) до зависимых дизайн-решений. Паспорт уточняет ту же основу; известные ответы используй, новые сохраняй. Проверка макета дополняет программу приёмки свойствами, которые предстоит проверить в работающем UI.

Из brief, текущего продукта, относящихся решений и просмотренных примеров зафиксируй:

| Часть | Достаточная запись |
| --- | --- |
| Цель и сценарий | Для кого и зачем экран; вход/исходные данные → главное действие → заметный результат и завершение. Существенные переходы, отказ и восстановление уточняет [interaction-quality](interaction-quality.md) |
| Условия | Маршрут/место в продукте, целевое устройство и ввод; известная рабочая область окна в CSS px, масштаб/zoom, если влияет. Нужные дополнительные размеры и причина их выбора; неизвестное обозначь явно |
| Визуальная система | Ссылки на существующие компоненты/токены, роли текста/цвета, плотность и композиционный принцип. Сохраняй одну систему; новое направление опиши наблюдаемыми признаками |
| Основания и сохраняемое | Просмотренные референсы/принятые экраны и конкретные переносимые качества; важные решения, причина и источник. Укажи действия, данные и характер, которые должны сохраниться |
| Проверка и версия | Критерии успеха, обязательные представления и способ проверки; версия основы и ссылки на артефакты. Различай выбор автора, агентскую проверку и фактическую приёмку пользователь |

Референс обосновывает конкретный приём, а не целиком заменяет продуктовый сценарий. Критическое неизвестное разрешай по [reference-grounding](../../product-engineering/references/reference-grounding.md); только зависимая работа ждёт его разрешения. Известные условия используй без повторного интервью.

Для нового лендинга или исследовательского дашборда учти [принятые UI-уроки](accepted-ui-lessons.md): содержательный путь после первого экрана, роли иллюстраций/цвета и последовательность объяснения данных. Применяй их к цели и принятому стилю проекта.

**Готово:** цель, действие, стиль, сохраняемое и условия проверки определены; критические предположения видны и имеют способ проверки.

## 2. Связать экраны, состояния и размеры

Обозначь проверяемую точку как **экран/маршрут + состояние + данные + размер окна**. Составь компактную карту переходов или таблицу в существующем плане: откуда пришёл пользователь, что сделал, что изменилось, как вернуться и что сохранилось. Покрой основной непрерывный путь и существенный для риска отказ/возврат. Loading, empty, error, success, focus и прочие состояния добавляй по фактическому сценарию.

Проверь согласованность одного объекта, выбора, единиц, фильтров и результата между представлениями. Связанные состояния используют те же компоненты и смысловые роли. Для каждого нужного размера укажи, что переносится, сворачивается или остаётся доступным. Представительные сочетания и рискованные границы достаточны; полный перебор всех состояний на всех размерах нужен только при соответствующем риске. Desktop-сценарий не получает мобильную версию автоматически.

**Готово:** по карте можно пройти от входа до результата и восстановления; важное состояние/размер не исчезает из проверки, противоречия данных и поведения устранены.

## 3. Проверить макет или прототип до полной реализации

Выбери самый дешёвый носитель, способный проверить спорное свойство: sketch/wireframe для структуры, оформленный ключевой экран для стиля и иерархии, связанный или работающий прототип для переходов. Допустим ограниченный прототип в коде. Черновой wireframe не подтверждает типографику, а статичная картинка — рабочее взаимодействие. При новом визуальном направлении добавь достаточный оформленный фрагмент; при принятой системе используй её реальные компоненты/образцы.

Оформленный фрагмент проверяй с представительным контентом: реальными длинами подписей, единицами/датами, нужной геометрией графика и существенной иллюстрацией в целевом размере. Замена этих элементов нейтральными заглушками оставляет их считывание непроверенным.

Сначала зафиксируй первое считывание по [протоколу восприятия](../../product-engineering/references/human-perspective-review.md), затем оцени основу:

| Критерий | Наблюдаемое свидетельство |
| --- | --- |
| Сценарий и функция | Главное действие обнаружимо, обещание и результат совпадают; ошибку/возврат можно объяснить по связанным состояниям |
| Согласованность | Данные, компоненты и состояния описывают один сценарий; переход не теряет важный контекст без причины |
| Стиль и контекст | Принятые признаки, контент и плотность подходят продукту и целевому окну; референсные приёмы помогают задаче |
| Понятность и доступность | Иерархия и подписи объясняют действие без пояснения автора; существенные клавиатурные/focus и адаптивные решения предусмотрены |

Дефект → гипотеза причины → изменение основы → повтор затронутого сценария. При изменении общего решения обнови связанные состояния/размеры. Зафиксируй текущую версию основы, просмотренные представления, наблюдения и ограничения. Показ и ожидание ответа следуют выбранному режиму участия из задания. В автономном режиме обычная самопроверка выполняется без нового одобрения; существенный ещё не согласованный выбор требует решения пользователь.

**Переход к полной реализации:** критические противоречия макета устранены, основной путь и нужные крайние случаи рассмотрены, основание дизайна сохранено. Свойства, доступные только в работающем UI, перечислены для последующей проверки. Для design-only запроса здесь заканчивается работа; готовность работающего интерфейса не заявляется.

## 4. Сравнить работающий UI с основой

Передай в [product-ui-review](../../product-ui-review/SKILL.md) паспорт/план, принятую версию макета, карту состояний и сохраняемые решения. Сравни реальный render с основой в сопоставимых точках: тот же маршрут, состояние, данные и размер/zoom. Сверь иерархию, компоненты/токены, плотность, контент и доступность главного действия; responsive-изменения оценивай по принятому правилу адаптации. Автоматическое наложение/diff может помогать, но совпадение пикселей не является универсальным критерием.

Отдельно зафиксируй **качество исходного дизайна**, **верность реализации основе** и **фактическую работу сценария**. Точный перенос плохого макета не делает UI готовым. Используй основной непрерывный сценарий, применимый отказ/восстановление и проверку сохраняемого из того же прохода product-ui-review; отдельный повтор для сравнения с макетом не нужен. Порядок фактического render и действий задаёт [visual-quality](../../product-ui-review/references/visual-quality.md).

Расхождение классифицируй как дефект переноса, обоснованную адаптацию или проблему основы. Сохрани исходную версию и причину изменения; при новом решении обнови основу и перепроверь затронутое. Релевантные свидетельства после изменений получают новую версию; неизменённые переиспользуются только при подтверждённой независимости. Для серии/повторного дефекта используй существующий quality-cycle/ledger, не новую систему статусов.

При аудите существующего UI без макета сравни с текущими требованиями, компонентами и исходными экранами; явно обозначь отсутствие проверенной проектной основы. Ретроспективное описание не доказывает preflight до реализации. Можно проверить UI в текущем состоянии, оставив сравнение с отсутствующим макетом непроверенным.

**Готово:** существенные расхождения объяснены или устранены, сценарий и сохраняемое проверены на текущей версии. Технические результаты, агентский осмотр и человеческая приёмка различаются; недоступные проверки остаются непроверенными.

## Пример соразмерного применения

Для desktop-таблицы: поиск записи → открытие карточки → возврат с сохранёнными фильтрами и выбранной строкой. Основа — текущая дизайн-система; представления — результаты поиска, нет совпадений/сброс, карточка и возврат, применимая ошибка. Макет проверяет иерархию и размещение в рабочем окне; ограниченный прототип — переходы. Рабочий UI затем проверяется на тех же данных и размерах реальным действием. Исправление отступа одной кнопки использует принятую основу и затронутые состояния этой кнопки.
