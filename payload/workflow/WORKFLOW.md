# Общий маршрут работы

Используй для многоэтапной задачи, нового создаваемого артефакта, неоднозначного пользовательского сценария, повторного дефекта или восстановления после сбоя. Для ясной небольшой правки достаточно затронутого этапа и проверки. Это маршрут текущего агента; права действий и дополнительных исполнителей определяют действующие AGENTS и указания пользователь.

## 1. Восстановить цель и выбрать ветку

Прочитай исходный запрос, названные документы/фидбек, относящиеся решения базы и текущее состояние проекта. Сначала исходные материалы, затем план исправлений и задание согласованному исполнителю. При продолжении или переделке адресно найди и прочитай связанные дополнения и поправки к названным обсуждениям; в существующем плане укажи, что включено, отложено с причиной или заменено последним решением. Полнота относится к этой цели, а не ко всему корпусу памяти. Историческая квитанция не доказывает нынешнюю работоспособность.

Зафиксируй ожидаемый результат, обязательные выходы, принятые решения, разрешённый объём и существенные неизвестные. Уже известное используй без повторного интервью. Вопрос нужен для существенного выбора, который не разрешён контекстом; независимые действия продолжай.

| Результат | Ветка |
| --- | --- |
| Разработка приложения/фичи | [product-engineering](../skills/product-engineering/SKILL.md); узкая задача сразу выбирает нужный product-* этап |
| Исследование | Источники → проверенные утверждения/неизвестное → понятный вывод; разработка подключается только при реализации |
| UI / дашборд | [product-ui-design](../skills/product-ui-design/SKILL.md) до композиции, [product-ui-review](../skills/product-ui-review/SKILL.md) после реального render; основной вопрос и действие важнее подробной справки |
| Интерактивное объяснение / визуальный мир | [visual-experiment-craft](../skills/visual-experiment-craft/SKILL.md), плюс UI-ветка для управления |
| Воксельная модель / набор | [voxel-model-craft](../skills/voxel-model-craft/SKILL.md), его 2D-preflight до нового подробного объёма |
| Текст, документ, изображение, презентация | Навык формата и замысел/аудитория; инженерные и UI-этапы только при соответствующем результате |
| Практический бытовой ответ | Прямой результат и нужные проверки, без проектного ритуала |
| Безопасность / reverse engineering | Общая рамка, проектная память, действующие границы и соответствующий маршрут |

При переработке принятой основы зафиксируй сохраняемые качества, действия и связи по [протоколу восприятия](../skills/product-engineering/references/human-perspective-review.md), с проверкой их переноса в новую версию.

**Выход:** понятны результат и ближайший этап; существенные связанные уточнения учтены. Загрузи его навык, подробные справки — по указанному триггеру.

## 2. Разрешить критическое неизвестное

Применяй [основания и референсы](../skills/product-engineering/references/reference-grounding.md), если у обязательной функции/пропорции/взаимодействия нет основания, источники противоречат, переиспользование стирает класс, признак нельзя оценить или дефект повторился без установленной причины. Уверенность агента не заменяет проверку. Исследование блокирует только зависимый шаг; обычный доступный ресёрч выполняй самостоятельно.

**Выход:** источник или допустимый авторский выбор → наблюдаемый признак → решение → способ проверки; важное оставшееся неизвестное названо.

## 3. Проверить дешёвое представление

Для нового замысла, серии или дорогой реализации сначала проверь один целый целевой сценарий и существенные крайние случаи в дешёвой форме. Представитель связывает части, нужные для результата: действие и отклик UI, эпизод видео в темпе, связный фрагмент документа, путь запроса через систему или сцену с окружением и деятельностью. Проверка отдельных компонентов покрывает только их свойства. Сверь стиль, функцию, контекст и понятность именно соединённого результата. При принятой неизменённой основе повторный дизайнерский этап не нужен.

Воксельная ветка использует существующий [2D design preflight](../skills/voxel-model-craft/references/design-preflight.md), включая согласованные виды и масштаб набора. Реализм, детализация и декоративность — разные решения; сохрани одобренный характер.

**Выход:** структура и действие объяснимы, критические противоречия устранены до массового/дорогого шага. Самостоятельная проверка не создаёт нового запроса одобрения.

## 4. Создать и сохранить состояние

Выполняй согласованный объём полезными завершёнными частями. Для длинной работы используй существующий план либо [task-state](../skills/product-engineering/references/task-state.md). Список обязательных выходов задай до серии: исчезнувший объект должен быть обнаружим. Результат этапа содержит артефакт/версию, свидетельства, статус, открытое и следующий шаг.

После сбоя восстанови выполненное и принятые решения; повтори затронутый шаг по новой гипотезе. Пользовательская остановка не разрешает фоновый перезапуск. Неизвестные зависимости требуют консервативной перепроверки; описанная и проверенная независимость позволяет сохранить незатронутые результаты.

**Выход:** получены запланированные артефакты; отсутствующий, частичный, устаревший, неуспешный и внешне заблокированный результат различаются.

## 5. Посмотреть и проверить как пользователь

Для результата, который человек воспринимает или использует, применяй [единый протокол восприятия](../skills/product-engineering/references/human-perspective-review.md). Отдельно проверь техническую корректность, смысл/функцию и фактическое считывание/использование. Реальный UI требует действий, анимация — просмотра движения, документ — чтения/просмотра, 3D — функциональных видов и масштаба. Недоступная модальность остаётся непроверенной.

Для серии/процедуры/повторного дефекта используй [quality-cycle](../skills/product-engineering/references/quality-cycle.md) и ledger. Автор сам тестирует результат, готовит подробное задание и запускает нового независимого проверяющего на каждый раунд приёмки по [порядку ревью](independent-review.md). Разделение ответственности, бриф и постоянное разрешение заданы там; полный набор авторских тестов автоматически на ревью не переносится.

**Выход:** каждый pass относится к точно названному свойству, условиям и достаточной модальности свидетельства по протоколу восприятия. Существенное непокрытое свойство остаётся непроверенным. Автоматический pass, агентский осмотр и человеческий отзыв имеют отдельные статусы.

## 6. Исправить и завершить

Наблюдение → проверка причины → минимальная достаточная правка → повтор исходного сценария → регрессия сохраняемого. Новый раунд требует оставшегося существенного дефекта или новой гипотезы; выполненная приёмка не требует бесконечной полировки. Повторять согласие на обычное продолжение не нужно.

Проверь полноту обязательных выходов и актуальность свидетельств. Для задачи с состоянием используй `agent-worklog.mjs inspect`, для ledger — `validate --require-ready`. Контроллер проверяет записи и файлы, не удостоверяет мысль или красоту. Реальный блокер сохраняется с конкретной зависимостью и минимальным следующим действием.

**Выход:** результат, проверки, ограничения и следующий шаг различимы; непроведённая проверка не получает зелёный статус.

## 7. Передать урок

Через kb-save сохрани новый полезный итог, путь к текущему handoff и статус. Урок: триггер → наблюдение → механизм/гипотеза → проверка → пример/контрпример → область/исключение → версия. Общее правило хранится один раз; предметное — в профильной справке, значения — в проекте. Загружай близкие примеры, а не весь исследовательский корпус.

Для проверочной задачи используй [пилот и метрики](../skills/product-engineering/references/workflow-pilot.md). Наличие инструкции, правильное восстановление примера и улучшение незнакомого результата — разные утверждения.
