# Work route

This is the current agent's route, not a list of mandatory skills. AGENTS and the user's latest instructions determine permissions. A clear local task starts at its affected stage.

1. **Recover the task and its intent.** Establish the request, material corrections, current result, authorized scope and next verifiable step. For a new substantial or ambiguous task, a revision of accepted work, or work on the user's own material, use the [task brief and acceptance]({{HARNESS_ROOT}}/skills/dev-flow/references/task-brief-and-acceptance.md): the intent card, questions that change the work, a short playback of your understanding, a saved basis, the user's participation and a separate review choice. The user's own material is the basis; your changes are proposals. Match the scale of change to the request. Reuse known answers.
2. **Choose one primary stage.** Open its skill, then follow the references it names for this kind of deliverable until you reach the specific criteria, accepted lessons and examples; read them before planning. A task with several deliverables (for example, an analysis presented as a dashboard) opens the skill for each. A guide already read in this context need not be reread unless it changed. On transition/recovery, read the current basis and task state, then only changed or lost instructions that are needed.
3. **Resolve risk before an expensive step.** If a critical property lacks support, sources conflict or a defect recurs without an explanation, use [reference-grounding]({{HARNESS_ROOT}}/skills/dev-flow/references/reference-grounding.md). For an expensive new direction, check the smallest coherent representation that distinguishes the disputed property. When the direction is open, compare at least two materially different approaches against the intent card and recommend one with its main tradeoff; for a creative concept or a new interface or redesign direction, use [creative-direction]({{HARNESS_ROOT}}/skills/creative-direction/SKILL.md). Before committing, check the cheap representation against the intent card's likely rejection reasons. Selected human checkpoints are mandatory before dependent work continues.
4. **Produce a useful result.** Complete the agreed scope in finished pieces. Keep requirements/decisions, current version, checks, material open issues and next step in one existing plan. A machine graph/ledger is needed for a real series, complex dependencies or a project requirement; it references the plan instead of duplicating it.
5. **Verify the result.** Check current requirements and the acceptance program using the [shared reference](../skills/dev-flow/references/task-brief-and-acceptance.md). Perform proportional technical checks and actual use/inspection in the required modality. Before reporting a result a person will see, read or use, do the quick start of the [human-perspective protocol]({{HARNESS_ROOT}}/skills/dev-flow/references/human-perspective-review.md): open it as the user will, record the first impression, compare side by side with the accepted version or the user's material, and check the user's likely objections. For style, recognition and clarity, continue with its detailed method: direct comparison with the basis, correct change membership and preservation. Unknowns remain unverified. Distinguish author, independent and human assessments; perform [separate review]({{HARNESS_ROOT}}/workflow/independent-review.md) only when selected.
6. **Repair and finish.** Confirm the cause, fix it, repeat the original failing case and affected regression. A round needs a new signal, confirmed defect or testable hypothesis; the same inspection does not create new evidence. Preserve the failure/correction and current status without rewriting history. Deliver results with checks and limitations; save a useful new lesson through kb-save with its applicability limits.

Before planning the structure of a dashboard or report, read the research-dashboard sections of [accepted UI lessons]({{HARNESS_ROOT}}/skills/ui-design/references/accepted-ui-lessons.md), including the accepted example. Before implementing a new dashboard or substantial UI redesign, run a targeted ui-reference search and inspect relevant real examples. Connect selected techniques to the user's main question and action; use one design system. The user's target device and actual window width determine verification. A dashboard shows relationships/comparisons/conclusions, updates graphics and labels consistently, and identifies assumptions and numerical grounds. Add mobile coverage when the task requires it, not because it says “landing page.”

Specialist documents hold subject-specific criteria. Do not retell shared requirements/state/permission procedures in every branch. Open historical research and accepted examples when they match the current deliverable or question.

For a series or recurring semantic defect, [quality-cycle](../skills/dev-flow/references/quality-cycle.md) adds representative selection and protection of accepted examples. Comparative experiments use one [workflow-pilot](../skills/dev-flow/references/workflow-pilot.md); ordinary instruction edits do not trigger it.

Shared procedure owners: questions/basis/criteria — task-brief-and-acceptance; observation and preservation — human-perspective-review; machine state — task-state; evidence records — quality-ledger; an agreed second view — independent-review. A specialist pointer does not require repeating a procedure or rereading an unchanged guide. One current pass may support several criteria when its conditions and observations suffice for each.
